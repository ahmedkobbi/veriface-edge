# VeriFace Edge — Change Management Documentation (SOC 2 CC8)

## Overview

This document describes the change management process for VeriFace Edge, mapping to SOC 2 Common Criteria CC8 (Change Management).

---

## CC8.1: Change Authorization

### Pull Request Workflow

All changes to the VeriFace Edge codebase follow this process:

1. **Create branch** from `main`:
   ```bash
   git checkout -b feat/description
   ```

2. **Make changes** following the code style guidelines (see `CONTRIBUTING.md`)

3. **Open Pull Request** against `main`
   - PR template (`.github/PULL_REQUEST_TEMPLATE.md`) requires:
     - Description of changes
     - Type of change (bug, feature, breaking, security, etc.)
     - Security checklist (no secrets logged, inputs validated, etc.)
     - Testing checklist (tests added, TypeScript compiles, linting passes)

4. **Code review** by at least 1 reviewer
   - Reviewer checks: code quality, security, test coverage, documentation
   - Breaking changes require admin approval
   - Security-sensitive changes require security review

5. **Merge** by admin (only after all checks pass)

### Authorization Levels

| Change Type | Authorization Required |
|-------------|----------------------|
| Bug fix (non-breaking) | 1 reviewer + CI passes |
| New feature (non-breaking) | 1 reviewer + CI passes |
| Breaking change | Admin approval + 1 reviewer + CI passes |
| Security fix | Security review + admin approval + CI passes |
| Infrastructure change (Docker, CI/CD, nginx) | Admin approval + 1 reviewer |
| Cryptography change | Security review + admin approval + cryptographic review |
| Database schema change | Admin approval + migration tested in staging |

## CC8.2: Change Testing

### CI/CD Pipeline

Every PR triggers the CI pipeline (`.github/workflows/ci.yml`):

```
Push/PR → Lint → Type Check → Unit Tests → Integration Tests → Security Scan → Build
```

| Stage | What It Checks | Required |
|-------|---------------|----------|
| **Lint** | ESLint code style | ✅ Must pass |
| **Type Check** | `bunx tsc --noEmit` | ✅ Must pass |
| **Unit Tests** | `bun test` (162+ tests) | ✅ Must pass |
| **Integration Tests** | API endpoint tests with real DB | ✅ Must pass |
| **Security Scan** | CodeQL analysis + `bun audit` | ⚠️ Warnings allowed, errors fail |
| **Build** | Docker image build | ✅ Must pass (main branch only) |

### Native SDK CI

Separate workflows for native SDKs:
- `sdk-ios.yml` — macOS runner, `swift build` + `swift test`
- `sdk-android.yml` — Ubuntu runner, `gradle assembleRelease` + unit tests
- `sdk-flutter.yml` — Ubuntu runner, `flutter analyze` + `dart test`

### Test Coverage Requirements

| Component | Minimum Coverage |
|-----------|-----------------|
| Crypto primitives (Ed25519, X25519, AES-GCM, BLAKE3, HKDF) | 90% |
| API endpoints | 80% |
| SDK public API | 80% |
| Admin UI | Manual testing (12 device sizes) |
| ZK circuits | Formal verification (Picus) — planned |

## CC8.3: Change Approval

### Merge Requirements

- All CI checks must pass (green)
- At least 1 code review approval
- No merge conflicts
- Branch is up to date with `main`

### Release Process

1. **Tag the release**: `git tag v1.1.0 && git push origin v1.1.0`
2. **Release workflow** (`.github/workflows/release.yml`) auto-triggers:
   - Builds changelog from commits since last tag
   - Creates GitHub Release with auto-generated notes
   - Publishes to npm / CocoaPods / Maven / pub.dev (if configured)
3. **Deployment workflow** (`.github/workflows/ci.yml`):
   - Builds Docker image
   - Deploys to staging
   - Manual approval for production
   - `kubectl set image deployment/veriface-edge ...`

## CC8.4: Change Documentation

### Commit Conventions

Uses [Conventional Commits](https://www.conventionalcommits.org/):

| Type | Use For |
|------|---------|
| `feat:` | New features |
| `fix:` | Bug fixes |
| `security:` | Security fixes |
| `breaking:` | Breaking changes (with `!`) |
| `docs:` | Documentation |
| `test:` | Test additions |
| `refactor:` | Code refactoring |
| `chore:` | Build, dependencies, tooling |

### Changelog

- Auto-generated by the release workflow from commit messages
- Published in GitHub Release notes
- Includes: features, fixes, breaking changes, security updates, migration notes

### Audit Trail

- All deployments logged to audit chain (event type: `key.rotated` with `action: deployment`)
- Git history preserved (no force-push to `main` without admin approval)
- PR history retained permanently on GitHub

## CC8.5: Production Changes

### Deployment Pipeline

```
main branch (merge)
    │
    ▼
GitHub Actions CI
    ├── Build Docker image (multi-stage, non-root)
    ├── Push to GitHub Container Registry
    └── Deploy to staging
         │
         ▼
    Staging verification
    ├── Health check (curl /api/health)
    ├── Smoke tests (auth flow, API key creation)
    └── Manual approval
         │
         ▼
    Production deployment
    ├── kubectl set image (rolling update)
    ├── Health check (3 consecutive successes)
    └── Monitor for 30 minutes
```

### Rollback

If deployment fails or issues are detected:

```bash
# Immediate rollback to previous version
kubectl rollout undo deployment/veriface-edge

# Verify rollback
kubectl rollout status deployment/veriface-edge
curl https://api.veriface.io/api/health
```

### Database Migrations

- Schema changes via Prisma migrations (`prisma migrate dev`)
- Migrations tested in staging before production
- Breaking schema changes require:
  1. Backward-compatible migration (add column, don't remove)
  2. Deploy code that uses new column
  3. Backfill data
  4. Deploy code that removes old column
  5. Migration to remove old column

### Emergency Changes

For critical security fixes (SEV-1):

1. Create hotfix branch from `main`
2. Apply fix + add tests
3. Expedited review (1 reviewer, admin approval)
4. Fast-track CI (skip non-critical checks)
5. Deploy directly to production
6. Post-incident review within 48 hours

## Change Classification

| Change Type | Examples | Process |
|-------------|---------|---------|
| **Standard** | Bug fix, new feature, docs | Normal PR + CI + review |
| **Security** | Crypto change, vuln fix, auth change | Security review + admin approval |
| **Breaking** | API change, schema change, config change | Migration plan + admin approval + release notes |
| **Emergency** | Critical security fix, data corruption | Hotfix process + post-incident review |
| **Infrastructure** | Docker, CI/CD, nginx, DNS | Admin approval + staging test |
